# GraphSmith v0.5.0 — Distribution & Discovery — Claude Code Kickoff Prompt

**Status:** ready to start. All four open decisions resolved and approved by Paul 2026-07-30 (see `EXTRACTION-SYNTHESIS.md` addendum in this same folder). **Not gated behind v0.4.0** — different files, no security-tier review needed, can run in parallel on its own branch.

**Paste this whole document as your first message in a fresh Claude Code session**, on a new branch/worktree (see the "Before you start" note at the bottom — do not run this on the shared checkout while `v0.4.0/build` is active there).

---

## Mission, in one paragraph

Build the four pieces that let GraphSmith install itself trivially, and honestly, across the agent hosts people actually use: an idempotent reconciler that safely maintains a GraphSmith block inside a file like `AGENTS.md` without ever touching the user's own content; a real Claude Code plugin with lifecycle hooks (zero footprint in the target repo); an MCP server that hands back current GraphSmith guidance as a tool response, built natively against the new stateless MCP spec; and a generator that produces every other host's format from one canonical source instead of hand-copying N files and hoping a CI diff-check catches drift. This is a distribution/UX build, not a security build — nothing here makes an attestation claim, and nothing here should ever claim to *enforce* anything it injects.

## Where this came from

Extracted from a source-level review of `microsoft/clarity-agent` and `DietrichGebert/ponytail` (both MIT). Full research, ranked ADOPT/ADAPT/REJECT verdicts with file:line citations, and the reasoning behind every decision below live in `EXTRACTION-SYNTHESIS.md` in this folder — **read that file in full before starting Wave 0.** The short version: neither source repo solves cold-start discovery (an agent in a repo that's never heard of GraphSmith still won't find it), but both have real, usable installation-plumbing patterns, and one hard lesson threads through everything here — **a green "it's working" claim is worse than an honest "not yet" if the mechanism underneath doesn't actually do what it claims.** GraphSmith's own team learned this the expensive way on the capability-enforcement engine (`graphsmith-capability-enforcement-withdrawn-2026-07-29.md` — read this too, it's short and it's the standard everything below is held to).

## The four resolved decisions (do not relitigate these — build to them)

1. **Version/scope:** this is v0.5.0, runs on its own branch, merges independently of v0.4.0's timeline.
2. **Canonical source:** root `SKILL.md` — which already exists in this repo and is already the file `npx skills add`/agentskills.io consume — is the single master copy. **Correction made during Wave 0:** the original version of this decision proposed creating a new `.graphsmith/skill.md`; reading the live repo before writing anything found that would just recreate the AGENTS.md-style dual-source-of-truth conflict one level up, so no new file is created. `AGENTS.md` is **not** special — it is one more surface the generator renders and the reconciler places, exactly like every other single-file host surface. Lane A never treats `AGENTS.md` (or `SKILL.md`) as anything it writes to; Lane D never treats `AGENTS.md` as anything but an output target, and never writes to `SKILL.md`.
3. **Host scope at launch:** four surfaces — the free AGENTS.md-generic tier, Claude Code (plugin + hooks), Cursor, GitHub Copilot. Everything else (Windsurf, Cline, Qoder, etc.) is an explicit non-goal for this release, added later as independent small PRs once the generator exists and there's a concrete signal (a user ask, an issue) to build for a specific host — do not build speculative adapters for hosts nobody has asked for.
4. **Lane C is stateless-MCP-native**, built against the MCP spec's 2026-07-28 revision (SEP-2575, "Make MCP Stateless" — Final), with the legacy `initialize` handshake kept as a compatibility fallback until we've confirmed which protocol version the MCP clients we actually target (starting with Claude Code's own) currently speak. **The full technical detail for this is in the separate Wave 0 prompt** — read it before designing Lane C; this spec is two days old as of this writing and your training data almost certainly predates it, so do not rely on prior knowledge of MCP session/initialize semantics for this lane.

## Build discipline (mirrors the project's existing v0.3.0/v0.4.0 discipline, scaled to this build's actual risk level)

This is **not** security-tier work — nothing here makes an attestation claim, so there's no false-green risk of the kind that killed the capability-enforcement engine. But it touches real user files (`AGENTS.md`, global Claude Code config) with real data-loss risk if done carelessly, so it still earns genuine independent review, just not the full ≥2-non-Anthropic-family bar reserved for GSA/attestation work.

- **One writer per lane.** Use the Task tool to spawn one subagent per Wave 1 lane (A, B, C, D). No shared-file contention — Wave 0 exists precisely so the lanes don't have to coordinate mid-build.
- **Builder ≠ reviewer, every lane.** After each lane's builder subagent reports done, spawn a *separate* reviewer subagent — different context, same or different model family is fine here (not security-tier) — armed with that lane's acceptance criteria **and** its adversarial attack list below. The reviewer's job includes picking its own negative controls/mutations to test with. **Do not let the builder propose the adversarial tests for its own code** — that is the exact failure pattern documented in the capability-enforcement postmortem (a builder's self-chosen mutant tends to test only what the builder already thought of, which is why four consecutive "fixed and verified" rounds were each still broken).
- **A fifth, cross-lane integration reviewer**, after Wave 1, whose only job is hunting for lanes making incompatible assumptions about shared state — this is exactly the class of bug that produced the AGENTS.md dual-ownership conflict this build already resolved once at the design stage; assume there are others like it waiting at the integration boundary.
- **You (the orchestrating Claude Code session) re-run every test yourself** before accepting a lane as done — never trust a subagent's self-reported "tests pass." This is non-negotiable regardless of tier; it has nothing to do with security specifically, it's just what happens when the same judgment writes and grades a test.
- **Maintain `BUILD-LEDGER.md`** (git-ignored, same convention as v0.3.0/v0.4.0) so this build is resumable across sessions. Update it after every lane completes.
- **Honest-language + publication-hygiene lint** on every new piece of shipped copy (README additions, install docs, plugin descriptions). Add the new banned-phrase check from the synthesis doc: no "auto-discovered," "seamlessly discovered," or equivalent, anywhere — this build does not solve cold-repo discovery and must never imply it does. Say what's actually true instead: "one-command install across 4 hosts," which is a real improvement and doesn't need inflating.
- **RED-tier human gates carry over unchanged**: if anything in this build ever touches money, external sends, real-data deletion, or credentials (it shouldn't — flag immediately if a lane seems to be drifting toward any of those), halt for Paul, same as every other GraphSmith build.

## Wave structure

**Wave 0 — Freeze contracts (serial).** Already executed — see `WAVE-0-CANONICAL-SOURCE.md`, `WAVE-0-LANE-C-MCP-DESIGN.md`, and `schemas/host-adapter.schema.json` in this same folder/repo location for the frozen output, plus `WAVE-0-PROMPT.md` for the prompt used (note its canonical-source section is superseded by `WAVE-0-CANONICAL-SOURCE.md` — read that correction first). **HARD STOP at the end of Wave 0: produce a summary of the frozen `host-adapter.schema.json`, the `SKILL.md` canonical structure, and the Lane C stateless-MCP design, and wait for Paul's explicit approval before starting Wave 1.** Do not proceed past this stop on your own judgment — this mirrors the exact gate v0.3.0 and v0.4.0 used before their own parallel lanes started.

**Wave 1 — Parallel lanes**, one writer (subagent) each, started only after Paul's Wave 0 approval:

- **Lane A — Lane D's rendered output → `AGENTS.md` (and other reconciled-mode surfaces) reconciler.** Port the state-machine shape from `microsoft/clarity-agent`'s `snippet.py`/`ensure_agents_md` (marker-delimited begin/end block, versioned meta header, four-way state: absent→write, present-no-markers→append, present-current→no-op, present-drifted→splice-in-place). Generalize it: this reconciler places a *rendered* block (produced by Lane D) into any single-file surface, not just `AGENTS.md` — build it as a reusable primitive from day one, since Cursor and Copilot's single-file surfaces need the identical operation.
  - **Adversarial tests the reviewer must run:** symlink the target file out of the tree, confirm no write-through (this is the exact bug class — resolve-once-trust-forever — that killed the capability-enforcement engine on a different surface; do not let it recur here). Kill the process mid-write, confirm no partial/corrupted file (must be atomic: temp file + rename, never in-place). Put marker-lookalike text inside the user's own prose and confirm it's not misparsed as a real marker. Run two reconcile processes concurrently against the same file. Feed it CRLF, a BOM, mixed line endings. Run an old-schema-version reconciler against a file a newer one already spliced, and the reverse.

- **Lane B — Claude Code plugin + lifecycle hooks.** `.claude-plugin/marketplace.json` + `plugin.json` with a `hooks` pointer to a manifest registering `SessionStart` (inject current guidance into context) and `SubagentStart` (make Task-spawned subagents aware from day one — ponytail shipped this as a late fix for their own issue #252; we're not repeating that gap). Writes nothing into the target repo; all state lives in Claude Code's own config directory.
  - **Adversarial tests:** reproduce the Windows PowerShell stdin-swallowing class of bug ponytail hit (their issue #443) deliberately, don't just assume a timeout fallback handles every case. Install alongside a second hypothetical plugin that also registers `SessionStart` and confirm neither's output clobbers the other's. Kill the hook process mid-execution, confirm session start doesn't hang. Uninstall while another plugin shares a combined statusline/hook config and confirm only GraphSmith's own segment is removed — this is the specific scenario ponytail's `uninstall.js` was written to handle; replicate their care, don't skip it because it looks like polish.

- **Lane C — MCP server (instructions-carrier), stateless-native.** Full requirements in `WAVE-0-PROMPT.md` and the Wave 0 design doc it produces. Real, independently-publishable package (no ponytail-style reach-outside-package-directory `createRequire`) — must run from a bare `npm install` in an empty directory, not just from a full monorepo checkout.
  - **Adversarial tests:** fresh `npm install` in an empty dir with zero monorepo context, confirm it actually runs. Attempt an unauthenticated call against any network transport and confirm it's refused — this directly targets the exact gap found in `clarity-agent`'s MCP server (zero auth on its `sse`/`streamable-http` transports); do not ship that mistake here.

- **Lane D — canonical → all-surfaces generator.** Read root `SKILL.md` (read-only input — never written to), render the host-specific output for each of the four launch surfaces (AGENTS.md-generic, Cursor, Copilot — Claude Code is covered by Lane B's hooks, not this generator). Template: ponytail's `build-openclaw-skills.js` (rewrite only the host-specific frontmatter, copy the body verbatim) — but apply it to *every* surface from day one, not one surface with the rest hand-copied-and-diff-checked the way ponytail actually shipped it.
  - **Adversarial tests:** hand-edit a generated file directly, run CI, confirm it actually fails on that live edit (not just "confirm the check exists" — ponytail's own round-4-equivalent mistake was staging a negative control the broken code already caught, which proved nothing; don't repeat that shape of error here). Add a new host adapter, confirm existing surfaces produce zero diff. Feed the canonical source a construct valid in one host's frontmatter syntax but invalid in another's, confirm the generator fails loudly instead of emitting broken output silently. **Added post-Wave-0 (2026-08-01, extracted from an independent review of `cosmtrek/mindwalk`'s adapter-schema testing discipline):** for each of the four real launch adapters, validate its *adapter definition file* (the JSON config in `generators/adapters/` — `id`, `displayName`, `targetPath`, `placementMode`, `outputFormat`, `bodyTransform`, etc.) against `schemas/host-adapter.schema.json` with a real JSON Schema draft 2020-12 validator — use `Ajv2020` from `ajv/dist/2020`, not the bare `ajv` default export, which validates against draft-07 and will mishandle this schema's `$schema`/`allOf`/`if`-`then` constructs — in CI. Schema-file-is-valid-JSON was already confirmed in Wave 0's adversarial review, but nobody has yet confirmed each adapter *definition* actually conforms to the schema it's supposed to be authored against, and those are different claims. **Note: `host-adapter.schema.json` describes the adapter *definition*, not the surface's rendered output.** Cursor's actual rendered file is Markdown with a YAML frontmatter block — structurally unlike this JSON config schema — so rendered output cannot be validated against the same schema; that would be validating the wrong artifact. A rendered-output contract is a real, separate thing worth having (e.g. per-`outputFormat` checks: frontmatter keys present and matching `frontmatterFields`, no frontmatter leakage for `markdown-plain`, `generatedFileHeader` placed correctly relative to the frontmatter block) — if wanted, scope and build it as its own adversarial test, don't assume this bullet already covers it. Also confirm determinism as a named, tested invariant, not an assumption: the same canonical `SKILL.md` + the same adapter definition must produce byte-identical output on every run — diff two consecutive runs and fail the test on any difference.

**Wave 2 — Integration + honesty pass (serial).** Compose Lanes A–D into the `graphsmith-skill` npm package and the already-deferred plugin-marketplace scaffold. Cross-lane integration reviewer runs (see Build discipline above) — specifically check Lane A + Lane D's shared handling of every single-file surface for the kind of ownership conflict already caught once at design time. Full honest-language lint pass. **HARD STOP: Paul's RC gate**, same as every prior release.

**Wave 3 — Release.** Cut alongside or shortly after v0.4.0 per the existing FF-1 public-surface-sync playbook. Update README/website/npm to describe the new install surfaces and the roadmap section.

## Success criteria (measurable — do not mark this build done until every one of these is actually demonstrated, not asserted)

1. Fresh install on a repo with an already-customized `AGENTS.md`: diff-test proves the user's existing content is unmodified outside GraphSmith's marker block.
2. Re-running install twice produces zero additional diff on the second run.
3. Claude Code: install → new session → GraphSmith guidance appears in context, verified via an actual hook-output assertion, with zero files written to the target repo.
4. All three non-Claude-Code launch surfaces (AGENTS.md-generic, Cursor, Copilot) are 100% generator-produced, zero hand-maintained files, CI-verified byte-identical to generator output.
5. The MCP server package installs and runs via a bare `npm install <package>` with no monorepo checkout dependency.
6. Honest-language lint passes on every new surface's copy, including the "no unearned discovery claims" check.
7. No claim anywhere in shipped copy implies enforcement of the content GraphSmith injects.

## Before you start (repo/branch hygiene)

Per the project's own standing hazard note: there is a single shared checkout on the build machine, and `v0.4.0/build` may still be active on it. **Do not `git checkout` on the shared checkout for this work.** Use `git worktree add ../graphsmith-v0.5.0 -b v0.5.0/build origin/main` (or equivalent) so this build lives in its own directory and can't pick up or leak stray commits the way a stray v0.4.0 commit once landed on `main` by accident. Confirm you're on a clean `v0.5.0/build` branch before touching anything.
