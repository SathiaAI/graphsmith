## Important — read this before you start on Lane C's design

Everything below about "stateless MCP" describes a real change to the Model Context Protocol specification that shipped **2026-07-28**, i.e. very recently. **Your training data almost certainly predates this and does not reflect it.** Do not rely on whatever you think you know about MCP's `initialize` handshake, session IDs, or `resources/subscribe` — that model is now the *legacy* path. The facts below are transcribed directly from the primary source (SEP-2575, "Make MCP Stateless," Final/Standards-Track, fetched and verified 2026-07-30) — treat them as ground truth for this design, not as something to second-guess against prior knowledge.

**What changed, mechanically:**
- The old mandatory `initialize` / `notifications/initialized` handshake — which established a session the server had to remember for every later request — is **removed**. There is no replacement handshake RPC.
- Every request is now self-contained. Protocol version travels as a mandatory HTTP header (`MCP-Protocol-Version: <version>`) that must match a `_meta` field in the request payload (`"io.modelcontextprotocol/protocolVersion"`), or the server returns `400 Bad Request`.
- Client identity and capabilities are no longer negotiated once. They travel on **every request** via `_meta`: `"io.modelcontextprotocol/clientInfo"` (name+version) and `"io.modelcontextprotocol/clientCapabilities"` (required — an empty object means the client supports nothing optional; servers must not infer capabilities from a prior request, because there is no "prior request" state to infer from).
- A new **`server/discover`** RPC (servers MUST implement it) replaces the handshake's capability-negotiation half — it returns `supportedVersions`, `capabilities`, `serverInfo`, and an optional `instructions` string. Clients MAY call it before anything else to learn what the server supports; they are not required to.
- `resources/subscribe`/`unsubscribe` are removed (subscriptions are inherently stateful). Replaced by a new **`subscriptions/listen`** RPC — a client opts into specific notification types (tool/prompt/resource-list-changed, or specific resource-URI updates) on a single request; the server's response is an SSE stream starting with an acknowledgment notification. This is the only place a long-lived connection still exists, and it's opt-in, not the default.
- Resumable SSE streams (`Last-Event-ID` reconnection) are **removed outright** — a dropped connection now implicitly cancels whatever request was in flight. Anything needing durability across a dropped connection must use the protocol's `tasks` primitive instead (fetch results after the fact), not a resumed stream.
- `ping` is removed in both directions (an ordinary RPC call already proves liveness; transport-level mechanisms handle connection health).
- **Security implication, stated directly in the spec's own Security Implications section: "Without a session handshake, every request must be independently authenticated and authorized." Implementations MUST ensure authentication is not bypassed by the removal of the initialization phase.** This is not optional or a nice-to-have for our Lane C design — it is the spec's own stated requirement, and it's exactly the gap that was found in `clarity-agent`'s MCP server (zero auth on its network transports) during the extraction research. Design Lane C so per-request auth is structurally required, not just documented as a best practice.
- **Backward compatibility is explicitly anticipated by the spec itself**: a server MAY support both old and new clients simultaneously — continue implementing the legacy `initialize` RPC for clients that still need it, while also exposing the new stateless RPCs (`server/discover`, etc.) for updated ones. A client that supports both should probe with `server/discover` first; if the server 400s or 404s that call, the client falls back to the legacy handshake.

**What this means for Lane C specifically:**
1. Design and build Lane C **stateless-native** — no session ID anywhere in the implementation, no `initialize` as the primary path. `server/discover` is mandatory; implement it.
2. **But also implement the legacy `initialize` handshake as a fallback**, per the spec's own documented dual-support pattern above, until we've confirmed which protocol version our actual target clients speak. **Before finalizing this, check what MCP client/SDK version the Claude Code build you're running actually ships with**, and note that in your Wave 0 summary — if it already speaks the 2026-07-28 spec, the legacy fallback can be deprioritized (but still built, cheaply, as the spec recommends); if it doesn't yet, the fallback is load-bearing, not optional, for launch.
3. Per-request auth (a bearer token or equivalent, checked on every call, no session to accidentally trust instead) is a **hard requirement** for any non-stdio transport, from the first line of code — do not ship an auth TODO the way `clarity-agent` effectively did.
4. Note in your design doc (don't build yet — this needs Paul's separate sign-off) that because a stateless server has no reason to be pinned to one machine, Lane C's architecture should not assume "runs locally on the user's machine" as the only deployment shape — a horizontally-scaled or serverless hosted deployment is now a legitimate option, and would let an MCP-capable host point at GraphSmith's guidance via a single URL with nothing to install locally at all. Flag this as a real possibility for a future release, not something to build in Wave 1 — scope Lane C for Wave 1 to "runs correctly as a local stdio/HTTP process," and record the hosted option as a noted opportunity for Paul to decide on separately.
5. Flag explicitly, in your summary, whether Lane C and the already-planned v0.3.0 MCP attestation shim (`graphsmith-v0.3.0-mcp-attestation-shim-design.md` — read it if available in this checkout) should share one stateless deployment exposing both as separate tools/methods (using the new header-based method routing some implementers are using for gateway-level dispatch), or stay as two separate servers.
