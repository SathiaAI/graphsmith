# v0.5.0 Wave 0 — Lane C (MCP server) design, stateless-native

Per the resolved Decision 4. Design only — no code in this commit; Lane C's builder subagent implements this in Wave 1.

## Tool surface

One tool: `graphsmith_guidance`. Read-only. No arguments accepted, not just "none required" — its input schema is `{type: "object", properties: {}, additionalProperties: false}`, so a client passing unexpected arguments gets a validation error rather than having them silently ignored. Returns the current `SKILL.md` body (the same canonical content Lane D renders from) as its result, mirroring the pattern found in both research repos (clarity-agent's `run_clarity`, ponytail's `ponytail_instructions`) — a tool call returns markdown instructions inline, so there is no separate registration step for "which guidance applies now." Kept to one tool deliberately: clarity-agent's 9-tool surface was found to be more than this use case needs, and every additional tool is more surface to keep in sync and more surface to secure.

## `server/discover` (mandatory per SEP-2575)

Returns `supportedVersions` (the 2026-07-28 spec version, plus whatever legacy version the `initialize` fallback below speaks), `capabilities` (advertises the single `graphsmith_guidance` tool, nothing else), `serverInfo` (name/version from `package.json`), and `instructions` (a short string pointing a client at `graphsmith_guidance` — the spec explicitly supports this field for exactly this purpose).

## Statelessness and auth

No session ID anywhere in the implementation. Every call to `graphsmith_guidance` is independently authenticated per SEP-2575's requirement — but note precisely what that requirement does and doesn't cover for stdio: SEP-2575 requires *authentication* (proving the caller is a valid MCP client speaking the protocol correctly), which the process boundary trivially satisfies for stdio (there is exactly one caller type — whatever process spawned this server over stdio). It says nothing about, and does not substitute for, *authorization to spawn the process in the first place* — that's an OS-level assumption MCP itself doesn't address, inherited from "only the intended host has a reason to launch this binary." That distinction matters because it's easy to conflate "authenticated per spec" with "provably only reachable by the intended coding-agent host," and they are not the same claim. No additional token is needed for stdio specifically under this framing, but the code must not silently assume a network transport will ever be safe to add without one, and this authentication/authorization distinction should be revisited explicitly if a second local caller of this binary, or any additional capability, is ever considered. If a network transport is added in a later release, per-request bearer-token auth is a hard prerequisite, not a follow-up — this is the exact gap found in `clarity-agent`'s MCP server (zero auth on `sse`/`streamable-http`) and it does not get repeated here.

Separately, SEP-2575 mandates per-request `_meta` validation on **every** RPC, not just `server/discover` — including the `graphsmith_guidance` tool call itself. The handler must check for `_meta["io.modelcontextprotocol/protocolVersion"]`, `clientInfo`, and `clientCapabilities` on each call, return `INVALID_PARAMS` if required fields are missing or malformed, and return `UNSUPPORTED_PROTOCOL_VERSION` (-32022) for a protocol version this server doesn't speak. This is not optional spec-compliance decoration — a Wave 1 build that only implements `server/discover` correctly and lets the actual tool-call path ignore `_meta` validation is non-compliant with the spec this design claims to follow.

## Legacy `initialize` fallback — RESOLVED, not deferred

**Corrected during adversarial review (2026-07-31):** the original version of this design left "is the legacy fallback load-bearing?" as an open question for the Wave 1 builder to check against Claude Code's installed MCP SDK version. An adversarial reviewer checked the actual state of the MCP SDK ecosystem as of SEP-2575's finalization (2026-07-28, three days before this correction) and found that only beta/pre-release builds of the Tier-1 SDKs speak the new stateless protocol — a stable `npm install`/`pip install` with no explicit pre-release flag still resolves to a version speaking the old, handshake-based protocol. There is no realistic scenario, three days after finalization, where a shipping Claude Code build already defaults to stateless-native. **Decision: the legacy `initialize`/`notifications/initialized` handshake is REQUIRED and LOAD-BEARING for Wave 1 launch, not an optional deprioritizable fallback.** Server implements it as the primary path a stock client will actually use today, while also exposing `server/discover` and the stateless per-request path for whenever the ecosystem catches up.

This also corrects what the "check" itself should verify. The original wording asked the builder to check "which protocol version the Claude Code build actually installed at build time speaks" — but that's ambiguous between two different things: (a) which server-side MCP SDK version *Lane C's own package* depends on, which is entirely within Lane C's control and tells you nothing about the client on the other end of stdio, versus (b) which protocol version the *Claude Code host binary itself* actually sends when it spawns an MCP server — an externally-versioned artifact Lane C doesn't control and that upgrades on its own release cadence. **The Wave 1 builder must verify (b), not (a)**: spawn the actual Claude Code binary being used for this build, observe whether its first message on the stdio channel is a legacy `initialize` request or a stateless-style request/`server/discover` probe, and record that finding in `BUILD-LEDGER.md`. Checking Lane C's own `package.json` dependency version proves nothing about client behavior and must not be treated as satisfying this check.

## Package shape

Independently publishable — `npm install` in an empty directory must work with no assumption of a monorepo checkout (the specific failure mode found in ponytail's `ponytail-mcp/`, which is `"private": true` and reaches outside its own package directory via `createRequire`, and therefore cannot ship standalone). GraphSmith's version reads `SKILL.md` via a path resolved relative to the *installed package's own* copy of it (the package's `files` allowlist must include `SKILL.md`), not via a relative path assuming a sibling checkout.

## Non-goals for Wave 1 (flagged, not decided)

- **Hosted/serverless deployment.** Because a stateless server has no reason to be pinned to one machine, a horizontally-scaled or serverless hosted deployment — letting any MCP-capable host reach GraphSmith's guidance via one URL, nothing installed locally — is a legitimate future option opened up specifically by the spec going stateless. Recording it here as a noted opportunity. Not in scope for Wave 1, which targets "runs correctly as a local stdio process" only.
- **Attestation-shim overlap.** Whether this tool and the already-planned v0.3.0 MCP attestation shim (`graphsmith-v0.3.0-mcp-attestation-shim-design.md`) should share one stateless deployment as two separate tools — using header-based method/tool routing for gateway-level dispatch if that ends up useful — is a real, live design question. **Presenting the tradeoff, not deciding it:** sharing one deployment means one auth story and one publish pipeline to maintain instead of two, but couples two conceptually different concerns (context-delivery plumbing vs. a trust/attestation primitive) into one release cadence and one blast radius if either has a bug. Recommend Paul confirm with whoever owns the attestation-shim design before Wave 1's Lane C builder commits to either shape.
