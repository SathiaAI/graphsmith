# GraphSmith Attestation (GSA) — Known Limitations

> **Evidence, not certification.** A valid GSA bundle records *what a run requested and produced, and that the record is unaltered* — it does not show the workflow is safe, correct, or compliant. This page consolidates the honesty boundaries stated across [`SECURITY.md`](.plans/v0.3.0/graphsmith-v0.3.0-SECURITY.md), the threat model's residual-risks section, the compliance-evidence crosswalk, and the README. Each limitation states the honest boundary and the control that *partially* addresses it. Nothing here is new scope — it is the scattered caveats gathered in one place.
>
> Language follows the repo's honest-language lint: results are **tested** (not "proven"), records are **tamper-evident** (not "tamper-proof"), pins are **hash-pinned**, external effects are **run-once / replay-verified** (not "exactly-once"), effect behaviour is described by **capability class**, and independent checking is **adversarial review**.

## 1. What GSA verifies
A conformant verifier runs the ordered §9 checks and fails closed at the first violation:
- **Manifest validity + path safety** — the manifest matches the schema; every artifact path is canonical (no traversal, no backslash, NFC).
- **Artifact integrity** — every artifact's recomputed raw-byte SHA-256 and length match the manifest (hash-bound).
- **Manifest + graph signatures** — the record is **tamper-evident**: any change to the manifest or the plan (graph / policy / skill-set hashes) invalidates the signature.
- **Recomputed control attestations** — all five controls are recomputed from the run's own evidence and must match what the bundle claims; a **contradictory bundle does not verify** (e.g. an executed unsigned skill alongside `all_skills_signed_and_approved=true`).
- **Profiles** — a profile the evidence does not support is downgraded to `unavailable`, never rendered green.

*Control:* the reference verifier (`scripts/gsa-verify.js`), exercised by the cross-family adversarial review recorded in `tests/gsa/ADJUDICATION.md`.

## 2. What GSA does NOT verify
- **That a workflow is safe, correct, or compliant.** A passing adversarial-review battery is a **floor**, not a proof of security, and never evidence of compliance to a regulator.
- **Model-level jailbreak / prompt-injection of the LLM itself.** GSA tests *architecture-level* injection resistance — that untrusted text is kept out of control flow and evolution paths — not model internals. *Control:* route model-jailbreak findings to dedicated LLM red-team tools through the external-tool seam, which records their results alongside the bundle.
- **The internals of third-party skills or external tools you install.** GSA records their provenance and runs them under the container capability class; it does not audit their code.
- **Anything with the documented controls disabled** (e.g. running with deterministic/enterprise-safe mode off). The attestation reports the posture it observed; it cannot vouch for a run that turned its controls off.
- **The compliance program itself** — data-layer access control and data minimisation at source; model validation, bias/fairness, and accuracy testing; the human-oversight *process*; risk classification / DPIA; vendor management; and the legal determination of compliance. GSA gives the verifiable technical substrate those programs stand on, and says so. *Control:* the compliance-evidence crosswalk maps each obligation to the control that produces evidence for it, and marks obligations with no executable control as manual-only — never covered.

## 3. Replay limitations
Replay recomputes the **deterministic** hashes from the bundle's own contents and confirms they reproduce. **Model-dependent steps are not replayable** — a run that called a model is reported `non_replayable`, shown as `unavailable`, never green. Replay confirms the record is internally reproducible; it does not re-execute external calls. *Control:* `scripts/gsa-plan.js` `replayBundle`, which lists non-replayable steps explicitly.

## 4. External side-effect limitations
The crash/recovery (chaos) harness tests exactly two properties: crash recovery, and **run-once, replay-verified** execution of *recorded* effects, with a loud halt when an external send's outcome is uncertain. This is **not** exactly-once against the outside world: true **single-delivery to an external system requires an idempotency key that system honours** (an `idempotent-by-key` capability-class declaration by the adapter author, not something GSA verifies). Every unresolved intent defaults to **reconciliation-required** until a rule affirmatively upgrades it. *Control:* the write-ahead intent + loud reconciliation halt (invariant I5) and the adapter capability classes in `contracts/06`.

## 5. Generated-skill limitations
GSA machine-evaluates only typed, schema-validated document/knob edits. **Generated code is never machine-applied** — code repairs are staged for a human through the four-gate pipeline. The `auto_skill_creation_disabled` control attestation records that no autonomously-created, unapproved skill ran in the same trust flow; if one did, the bundle does not verify that control. *Control:* the four-gate promotion pipeline (Gate 3 is propose-only; adoption requires explicit human confirmation) + the recomputed control attestation.

## 6. Per-skill capability limitations
GSA attests **only what is actually enforced**, per resource class:

| Class | Enforced? | By what |
|---|---|---|
| **network** | yes | supervisor destination allowlist; `--network none` under the container profile |
| **filesystem** | **no** | — see below |
| **subprocess** | **no** | — see below |
| **model** | **no** | no mechanism at this layer; needs a chokepoint in the model adapter |

**Per-skill filesystem, model and subprocess grants are NOT enforced.** A grant may declare them; nothing applies them, and the GSA capability attestation never marks them satisfied (decision D1: a class is attested only if it appears in the grant's `enforced` list, and only `network` ever does).

### Why this says "no" rather than "yes, with caveats"

An enforcement module was built on Node's Permission Model (`--permission`, `--allow-fs-read/write`) and **withdrawn**. Five rounds of adversarial review found successive ways for code inside the grant to read or write outside it, each round after the previous had been reported as fixed:

| # | Escape | Status when found |
|---|---|---|
| 1 | pre-existing **symlink** out of the tree | followed by the Permission Model; read `/etc/passwd` through one |
| 2 | pre-existing **hardlink** — a second *name* for the same inode | resolves *inside*, passes any symlink walk, and a **write** through it modifies the file outside |
| 3 | **stale audit** — clean at copy time, link planted after | evidence honest when produced, worthless when used |
| 4 | **forged spelling** — `<dir>/A/../real`, lexical vs physical | clean report for a tree nobody walked |
| 5 | audit contained against the copy, attestation about the **grant** | a link staying inside the copy while leaving the grant |
| 6 | **dangling symlink** | `realpath` fails so the audit skips it, but `open(O_CREAT)` follows it and creates the file at the target |
| 7 | a **granted path that is itself a symlink** | the audit never checked its own root |

The pattern across all seven is one thing: **the check was about a different boundary than the claim.** Each fix was narrower than the last, which is convergence — but the module was shipping a *green attestation*, and a false "enforced" in a signed bundle is worse than an honest "not enforced". So it was removed rather than shipped with a sixth round pending.

**What this costs:** nothing that was previously working. Per-skill grants were never enforced before this attempt either; this section previously said so, briefly said otherwise, and now says so again — accurately.

**What would be needed to do it properly:** the residual hole is a TOCTOU window no user-space audit can close — a link planted between the audit and `exec`. That needs the kernel: a bind mount with `nosuid`/`nodev`, a mount namespace, or a filesystem the enforced process cannot reach under any other name. A path-prefix check applied from user space to a tree an adversary can write to is the wrong tool, and the review history above is what that looks like in practice.

*Control (coarser than per-skill, and real):* the **container capability class** — a whole-run isolation boundary required for anything beyond typed edits (contract 04 B10). It runs untrusted code non-root, with all Linux capabilities dropped, `no-new-privileges`, a read-only rootfs and read-only source mount, network denied, and pid/memory/cpu caps. Each of those is verified by running a container through the real entry point (`evalenv.create("container")` → `runUntrustedCode()`) and reading `/proc/self/status` from inside — see `tests/evalenv/containment/`. That suite also asserts the profile still *functions* (the mount is readable) before making any containment claim, because an envelope nothing can run in is broken rather than secure.

## 7. Signer-trust limitations
GSA verification shows a bundle **was signed by the claimed key and is unaltered**. Whether to **trust that key is the verifier's policy** — an allowlist, an org key, or a transparency log (GSA-SPEC §5.5). The default is a local keypair, which attests "signed by *a* key"; cross-organisation non-repudiation is weaker until keyless / transparency-log signing (opt-in, targeted for a later draft). A **privileged local attacker** who can already rewrite the producer, the verifier, and the signing keys on the same machine is **out of scope, stated as such** — local self-verification detects same-user drift and mistakes, not a root adversary; CI cross-checking from a trusted workflow covers shared repositories. *Control:* the verifier-supplied trusted-key set + out-of-band maintainer signature for air-gapped verification (register Lane D, v0.3.0).

## 8. The state-store lock is not tied to a file descriptor
Exclusive access to `.graphsmith/state` is held by a **lock file plus an mtime and a pid**, not by the operating system. The textbook alternative — a lock whose lifetime is bound to the owner's open file descriptor, so that the kernel releases it the instant the owner dies — **cannot be built here at zero runtime dependencies**, and this is recorded as a limitation rather than tracked as pending work because nothing about it is pending.

Node exposes no file locking at all. On the exact runtime CI uses:

```
$ node -e "const fs=require('fs'); console.log(process.version, typeof fs.flock, fs.constants.O_EXLOCK)"
v22.22.2 undefined undefined
```

There is no `fs.flock`, no `fcntl`, no `O_EXLOCK`, and no `LOCK_*` constant on any supported platform. The three ways out are each worse than the limitation: a **native addon** (`fs-ext` and equivalents) requires prebuilds or `node-gyp` across {ubuntu, macos, windows} x node {18, 22} and ends GraphSmith's zero-dependency property, which is itself a security claim for something installed into a developer toolchain; **shelling out to `flock(1)`** is not portable — it is absent from a standard Windows environment and its availability on macOS is package-dependent; and `open(..., "wx")` / `mkdir`, which is what is used today, is genuinely atomic but is not bound to the process.

**What this costs, precisely.** Ownership has to be inferred from two observable facts instead of held by the kernel: is the owning pid observably alive, and has the lock been renewed recently. Both are approximations of the fact actually wanted, which is *"is the owner still making progress"*:

- a holder doing long work **without touching the store** renews nothing, so a sufficiently long non-store phase is stealable — the lock is only refreshed at the durable writes inside `_commit`;
- `pid` liveness is not owner identity. A crashed owner in a foreign pid namespace, or a recycled pid, can read as alive. This costs a bounded wait (at most one lease) and never a false steal, because a steal additionally requires the lock to have gone unrenewed;
- the age is a **wall-clock subtraction** against a filesystem mtime and is therefore not monotone. That one used to be a wedge — a lock whose mtime sat in the future was read as freshly renewed and refused indefinitely, including to `recover()` — and is now gated explicitly (contract 01 clause (d), `tests/state-store/clock-skew/`). The gate makes the failure honest; it does not make the mtime a reliable clock.

*Control:* both gates must agree before a lock is taken (`scripts/state-store.js`), renewal happens synchronously at every durable write rather than on a timer that could not fire, `_assertStillOwned` stops a superseded run **before** it writes rather than at release, and every reachable lock state is pinned by `tests/state-store/clock-skew/` with mutation controls.

**What would be needed to do it properly:** a decision that a native dependency is acceptable, *and* a real deployment with concurrent writers to justify it. Neither holds today — single-writer use does not exercise the gap, and adding a compiled dependency to remove a hazard that use does not reach would be a net loss in the property that matters more.

**Update (2026-08-26) — the zombie branch is now verified, not just reachable.** `pidAlive`'s `/proc`-based zombie check (a dead-but-unreaped owner reads as state `Z`) had been exercised by CI on Linux but never actually asserted against a real zombie — every prior test only ran it against live, non-zombie processes. `tests/state-store/pidalive-zombie/` closes that specific gap with a fixture that forges a genuine, self-verified Linux zombie (a `python3 os.fork()` child held unreaped) and asserts `pidAlive` returns `false` against it; see `.plans/v0.5.0/PIDALIVE-ZOMBIE-TEST-TRD-2026-08-24.md` for the design. This closes evidence for that one branch of `pidAlive` — it does not change the pid-reuse-across-namespaces or mtime-vs-wall-clock approximations described above, which remain.

## 9. Three of the shim's four capture modes remain unbuilt — the local-proxy mode now exists

`scripts/gsa-mcp-shim.js` (`sealBoundaryBundle`) takes an already-assembled `session` object — `initialize`, the granted `tools[]`, and the `calls[]` already made — and maps it into a signed boundary-tier (profile A) attestation bundle. That contract is unchanged and still narrow: the shim itself never observes an MCP connection directly, only the `session` shape it is handed.

**Update (2026-09-04) — deployment mode 1 (local proxy) is now built.** The design doc ([`.plans/v0.3.0/graphsmith-v0.3.0-mcp-attestation-shim-design.md`](.plans/v0.3.0/graphsmith-v0.3.0-mcp-attestation-shim-design.md), §4) describes four ways to produce that `session` object from a live MCP connection: a local proxy sitting between an MCP client and its servers, a client-side plugin hooking an agent's own MCP middleware, server-side middleware wrapping a tool server, and an integration point inside an enterprise MCP gateway. `scripts/gateway/` (`gateway.js`, `proxy.js`, `downstream.js`, `agent-transport.js`, `session.js`) is deployment mode 1: it sits between an agent and one or more real downstream MCP servers, speaks both legs of the protocol itself, builds the `session` object from the live traffic it proxies, and calls `chain.appendSession` (which calls `sealBoundaryBundle`) when each agent connection closes. See the Standalone Gateway TRD (`.plans/v0.5.0/STANDALONE-GATEWAY-TRD-2026-08-22.md`) for its design and section 10 below for that gateway's own residual scope limit.

**What still doesn't exist.** Modes 2–4 — a client-side plugin hooking an agent's own MCP middleware, server-side middleware wrapping a tool server, and an attachment point inside a THIRD-PARTY enterprise MCP gateway (distinct from this repo's own standalone one) — remain unbuilt. A caller who cannot or does not want to run this repo's own gateway process in front of their MCP traffic still has no capture path and must assemble the `session` object themselves, exactly as before this update.

*Control:* the shim's contract is narrow and honestly scoped — it never claims to observe anything beyond the `session` object it is given (the file's own header comment states the boundary-only, profile-A-never-full-profiles limit), and the produced bundle's `decision_record.md` states plainly that the agent's plan was not observed. There is no false "captured live" claim anywhere in the emitted bundle, and this document no longer claims zero capture paths exist now that one does.

**What would be needed to do it properly:** implement one of the remaining three deployment modes in §4 of the design doc, for callers who need capture without running this repo's own gateway process. That is unbuilt work, not a documentation gap.

## 10. The standalone gateway's HTTP agent sessions are keyed by an explicit session ID, with a bounded idle-timeout lifecycle (updated 2026-09-08)

**Superseded.** Until 2026-09-08 this section documented that `scripts/gateway/agent-transport.js`'s agent-facing HTTP listener identified a session by the underlying TCP socket (`req.socket`), and recorded a 2026-09-04 board decision to deliberately NOT build anything past that. Paul asked, informally, whether the HTTP transport should carry an explicit session identifier instead -- citing the MCP streamable-HTTP spec's own `Mcp-Session-Id` convention -- and said yes. Before building, this project sought a second opinion from an external panel of five non-Anthropic frontier models (openai/gpt-6-astra, x-ai/grok-4.5, google/gemini-3.1-pro-preview, deepseek/deepseek-v3.2, qwen/qwen3-max) on what scope was actually correct, since "yes" was compatible with a small labeling change or a much larger reconnect/resume rewrite. 4 of 5 recommended a socket-scoped ID that only fixes the naming/observability problem; x-ai/grok-4.5 dissented, arguing that leaves the actual pooling-proxy defect (below) unfixed and that a *coherent* minimal HTTP session model is not much more code. Paul chose grok-4.5's design. Full brief and all five raw responses: this project's decision log, entry "2026-09-08 -- external panel: HTTP agent session identity."

**What's implemented now.** Sessions are keyed by an explicit, server-minted `Mcp-Session-Id` (128 random bits), minted on a header-less `initialize` and returned on the response header. Every later request on that session must echo the header; an unrecognized/expired ID gets 404. A session ends on an explicit `DELETE` (204), after 30 minutes of inactivity (fixed for now -- not yet a config field, see `scripts/gateway/agent-transport.js`'s own header comment on why), or when the gateway process shuts down (`gateway.js#stop` already force-closes every session still open in `proxy.sessions`, unconditionally). The TCP socket that happened to carry a given request is no longer part of session identity at all -- this is still `session_boundary: "connection"` (the schema's only implemented value; `"time_window"` is still rejected at startup), just with "connection" now meaning "this MCP session," not "this TCP socket."

**What this fixes.** A connection-pooling reverse proxy multiplexing several distinct agents over one shared backend socket can no longer corrupt session identity (identity no longer comes from the socket at all), and one well-behaved agent whose HTTP client rotates connections mid-session (a recycled keep-alive socket, a client-side reconnect) no longer loses its already-`initialize`d session for a reason outside its control.

**What this deliberately still does NOT do -- disclosed, not hidden.** This is not full HTTP session resumption. There is no cross-process session store (a session dies with the gateway process, same as before), no session replay/recovery after a crash, and no configurable idle-timeout window yet. An agent that vanishes uncleanly (crash, network partition, no `DELETE`) now leaves its session open -- and counted in `active_sessions`, and un-sealed in the audit chain -- for up to the 30-minute idle window, instead of the near-instant cleanup the old socket-close handler gave for free; that is the deliberate trade for no longer conflating "this TCP connection ended" with "this agent is done." Building the fuller reconnect/replay/multi-node session store that a real `time_window` boundary would eventually need remains out of scope until a concrete deployment defines that lifecycle for real -- the same discipline the original 2026-09-04 decision applied, now to a narrower remaining gap.

*Control:* documented here, in `scripts/gateway/agent-transport.js`'s own header comment, and in the project's decision log (external panel brief + all five responses).

## 11. Gateway crash-recovery and idempotency fencing has a deliberately narrow guarantee, an operator-in-the-loop failure mode, and one untested layer (added 2026-09-09)

**Why this exists.** Two Codex findings on PR #29 exposed real gaps in `scripts/gateway/`: (Finding 1) a `tools/call` result lived only in memory until the whole agent connection closed, so a gateway crash between "downstream returned a result" and "the agent disconnects" silently dropped that evidence from the signed chain; (Finding 2) nothing tied a retried `tools/call` to its original attempt, so a timeout-then-retry on a side-effecting tool (email, payment, ...) could execute the downstream side effect twice. Per governance decision, this was not fixed unilaterally by the team that wrote the original code — an independent 5-model external panel (openai/gpt-6-astra, x-ai/grok-4.5, google/gemini-3.1-pro-preview, deepseek/deepseek-v3.2, qwen/qwen3-max) reviewed the problem and candidate designs first; this project's decision log and `option-c-hardened-design.md` carry the full brief, all five raw responses, and the synthesized design's documented divergences from each panelist.

**What's implemented.** `scripts/gateway/recovery.js`: a separate, unsigned, local-only store under `state_dir/gateway-recovery/` — an append-only per-connection WAL (`active/<connectionId>.jsonl`) recording `SESSION_START`/`INITIALIZE`/`CALL_START`/`CALL_RESULT`/`CLOSING` events, and one intent file per logical `(connectionId, tool, canonicalized-arguments)` operation (`intents/<intentKey>.json`) with a two-state terminal model — `dispatched -> completed | ambiguous` (no "failed": an explicit downstream error does not prove no side effect occurred, since a tool can commit an effect and still report failure). `proxy.js` consults an existing intent before ever dispatching a `tools/call`: a `completed` intent replays its cached result only if the retry presents the same caller-supplied idempotency key (`params._meta.idempotencyKey`) the original dispatch carried (JSON-RPC error `-32080 GATEWAY_AMBIGUOUS_RETRY` if still `dispatched`, `-32081 GATEWAY_DOWNSTREAM_OUTCOME_UNKNOWN` if `ambiguous`, `-32082 GATEWAY_TOOL_QUARANTINED_PENDING_OPERATOR_REVIEW` if a different connection this gateway's startup recovery flagged `pendingOperatorReview` still has an unresolved intent for this same tool — see the 2026-09-10 update below for both). `gateway.js#recoverCrashedSessions` runs once at startup, after the writer-claim is acquired and before any downstream connection starts, replaying any WAL a crashed prior instance left behind through `session.js`'s real, unmodified recorder functions; a call with no `CALL_RESULT` in the WAL is resolved from its real intent record if `completed` (this is precisely how Finding 1's gap is closed — from proof, never a guess), and left for an operator if not. A freshly-crashed unresolved call's intent is typically still `dispatched` at this point, not yet `ambiguous` — `buildHealthStatus`'s `recovery.pending_operator_review` field lists only `ambiguous` intents (an intent this gateway itself later fenced, e.g. via `closeConnection` on a live retry), while a `dispatched` one is counted in `recovery.in_flight` instead. The startup log's own `RECOVERY_AMBIGUOUS_INTENT` line (naming the connection and giving the exact `recovery-resolve`/`recovery-abandon` invocation) is the authoritative discovery path for this specific case, not `pending_operator_review` — which remains the right place to check for anything already known-ambiguous from ongoing operation between restarts. `downstream.js` also propagates the same intent key to the downstream as a conventional `graphsmith/idempotency_key` `_meta` field on both stdio and HTTP legs, for a downstream that itself understands one.

**What this deliberately does NOT guarantee — disclosed, not hidden.**

- **Not exactly-once execution.** The gateway will not knowingly issue a second downstream call for an operation whose outcome it cannot yet prove, from first dispatch until an operator explicitly resolves it. A different, uncoordinated caller hitting the same downstream directly, or a downstream that retries internally, is outside this gateway's control either way — where a downstream honors the propagated idempotency key, protection is stronger; where it's a black box, "halt and require a human" is the guarantee, not "guaranteed no duplicate."
- **The `dispatched`/`ambiguous` blocking fence is scoped to `(connectionId, tool, canonicalized-arguments)` only**, not (per one panelist's broader proposal) every effectful tool call on a downstream server considered together. Two different tools, or the same tool with even slightly different arguments, are never fenced against each other. A downstream whose side effects have cross-call interactions (e.g. two differently-worded calls that both happen to charge the same invoice) is not protected by this mechanism. (`completed`-intent replay is scoped differently as of the 2026-09-10 update below — see there.)
- **An `ambiguous` intent is never auto-expired by a TTL.** This is deliberate (every panelist proposed some auto-expiry; this design rejects all of them) — an unresolved ambiguous intent durably blocks any identical retry until an operator runs `recovery-resolve` (with real knowledge of what actually happened) or `recovery-abandon` (an explicit "I don't know and I'm giving up on finding out" override). The failure mode this trades into: an operator who never runs either command leaves that one specific operation permanently un-retryable through this gateway, indefinitely. That is the intended trade — silently expiring the fence would reopen exactly the double-dispatch risk this feature exists to close.
- **`recovery-abandon` deletes the intent fence it gives up on.** If the abandoned operation actually did execute downstream, a later identical call is no longer recognized as a retry and can re-run it. This is a knowing, per-connection, operator-invoked tradeoff (never automatic, never global) — documented here and in `gateway.js#abandonConnection`'s own header comment — for the case where waiting for certainty is no longer worth it.
- **Downstream `_meta` propagation is advisory, not enforced.** The gateway does not verify a downstream actually honors `graphsmith/idempotency_key`; a downstream that ignores it is unprotected at that layer, though still protected by the gateway-side fence, which is the actual mechanism this guarantee depends on.
- **Tool-level quarantine (2026-09-10 update, cluster E2) is a startup snapshot, not a live-updated list.** `pendingOperatorReviewConnections` is computed once, at this gateway process's own startup, from `recoverCrashedSessions`' return value. Since `recovery-resolve`/`recovery-abandon` require the writer-claim this live process already holds, nothing else can actually change those connections' outcome while this process stays up (see `recovery.js#resolveIntentNotExecuted`'s own header comment) — so the snapshot cannot go stale in practice, but this is a property of the writer-claim's single-writer model, not something the quarantine check itself enforces or re-verifies per call. It also does not close the gap for a tool that becomes ambiguous from a live (not-yet-recovered) crash between this process's own startup and its own eventual restart — only a crash a PRIOR process's startup already discovered and recovered is quarantined this way.
- **Scoped to real `tools/call` dispatch only.** An agent-initiated `sampling/createMessage` request forwarded through the same dispatch branch is explicitly out of scope for both the fence and the `_meta` propagation (see `proxy.js`'s and `downstream.js`'s own comments on this) — this only matters for the (unusual) case of an agent, rather than a downstream server, sending a sampling request through this gateway.
- **Recovery is proven at the unit/integration level, not against a real killed OS process.** `tests/gateway/recovery/run-tests.js` exercises `recoverCrashedSessions`/`abandonConnection` against WAL and intent fixtures built with the exact same `recovery.js` primitives `proxy.js` itself uses, replayed through the real `session.js`/`chain.js` code (not a parallel test-only implementation) — including the specific Finding-1 gap shape (intent completed, WAL missing the `CALL_RESULT` line) and a simulated "recovery crashed again mid-cleanup" repeat run. What is NOT covered is a true end-to-end test that spawns the real gateway CLI, `SIGKILL`s it mid-call, and asserts a second real process recovers it: `scripts/writer-claim.js`'s lease staleness window is not exposed as a `gateway-config.json` field, so such a test would either need to wait out the real (multi-heartbeat) staleness window — slow and disclosed as deliberately out of scope for this PR's test suite — or add a config passthrough to `writer-claim.js`/`config.js`, which this PR deliberately does not touch (out of scope: this fix is `recovery.js` + its call sites, not a writer-claim redesign). The gap this leaves untested is narrow: whether an actual `SIGKILL`'d process leaves the same durable, fsync'd WAL/intent files on disk that these tests construct directly — the same durability primitives (`state-store.js`'s `atomicCreateExclusive`/`atomicOverwriteFile`, and `appendDurableLine`) are already covered end-to-end for `chain.jsonl` by `tests/gateway/chain/run-tests.js`'s own "process killed mid-append" case (SS8 test plan item 12).

*Control:* documented here, in `option-c-hardened-design.md` (full panel brief, all five raw responses, and the synthesized design's point-by-point divergence from each), in `recovery.js`'s and `gateway.js#recoverCrashedSessions`/`abandonConnection`'s own header comments, and exercised by `tests/gateway/recovery/run-tests.js` and the Option-C-specific additions to `tests/gateway/proxy/run-tests.js`.

**Update (2026-09-09) — round-2 hardening from this PR's own review.** Six gaps found in the first implementation (all local to `recovery.js`/`gateway.js`/`proxy.js`'s own bookkeeping, none touching the identity/fencing model itself) are fixed: `walPath`/`intentPath` now reject a path-traversal-shaped `connectionId`/`intentKey` (relevant only to the `recovery-resolve`/`recovery-abandon` CLI's own flags and this module's exported API, not the gateway's own internally-generated IDs); the recovery directory is fsynced after every WAL/intent write, not just the file itself, matching `state-store.js`'s own convention; a `GATEWAY_BUNDLE_ID_COLLISION` during startup recovery is now content-verified (comparing the on-disk bundle's real `execution_trace` hash) before being trusted as "already durably appended," rather than assumed from the id match alone — `sealBoundaryBundle`'s `bundle_id` is a coarse fingerprint (`{init, grantedTools, n: calls.length}`) that two genuinely different crashed sessions could share; one connection's unreadable WAL/intent state (a permissions or I/O error, not a content one) no longer aborts recovery for every other connection in the same startup pass, and `recovery-abandon` can now quarantine (rename aside, not delete) such a connection without needing to re-read the state that made it unreadable in the first place; `recovery-resolve --confirmed executed` now requires `--result-file` (a missing one used to resolve with a `null` cached result, later replayed as an unverified clean success) and itself acquires the writer-claim (mirroring `recovery-abandon`, since both mutate the same intent files a live gateway's dispatch guard reads and writes); and `recovery-resolve --confirmed not-executed` now persists a terminal `not_executed` intent state instead of deleting the intent immediately, since deleting it left a crashed connection's still-pending WAL replay with nothing to distinguish "operator confirmed not executed" from "still unresolved" on the next restart — it would have been re-flagged for operator review forever. A dispatch blocked by the fence (`GATEWAY_AMBIGUOUS_RETRY`/`GATEWAY_DOWNSTREAM_OUTCOME_UNKNOWN`) is now also durably WAL-logged (a new `ANOMALY` event, replayed through `session.recordAnomaly` on recovery) rather than recorded in memory only, and both a blocked and a replayed call now get the same structured `gateway_call_completed` log line every other handled call gets.

**Update (2026-09-10) — E1/E2 hardening from PR #33's own review, escalated to the frontier panel per project governance.** PR #33's AI review (CodeRabbit + Codex) raised two architectural findings against this built implementation that were escalated to the same 5-model panel rather than fixed unilaterally (see `graphsmith-pr33-panel-verdict-pr29-round4-halt-status-2026-09-10.md`); Paul decided both in favor of the panel's narrower-scoped option.

- **Cluster E1 (identical-arguments over-fencing).** Two reviewers found that `(connectionId, tool, canonicalized-arguments)` alone cannot distinguish a genuine retry from two deliberate, intentional identical calls (e.g. two real `increment` calls) — the second used to silently receive the first's cached result instead of executing. Fixed: `completed`-intent replay now additionally requires the retry's `params._meta.idempotencyKey` to match the key the original dispatch carried. Without a match (no key, or a different key), the call dispatches as a new, independent operation — the completed intent record is superseded in place with a bumped `generation` counter under the same `intentKey` (still fenced against an in-flight/crashed retry of this new attempt), and the downstream-facing `graphsmith/idempotency_key` `_meta` value is suffixed with the generation (`<intentKey>.g<N>`) so a downstream implementing its own dedup does not mistake this new, independent call for the earlier, unrelated one. The `dispatched`/`ambiguous` blocking branches are unconditional and unaffected by any key — an unproven-outcome retry is a real double-dispatch risk independent of caller intent, which is why the panel (and Paul) rejected requiring a key everywhere.
- **Cluster E2 (reconnect bypasses the fence).** A reviewer found that a reconnecting agent gets a brand-new `connectionId` after a crash, so its retry of "the same" logical operation computes a different `intentKey` than the still-unresolved intent its crashed predecessor left behind — the exact-key lookup never sees it. Fixed narrowly rather than via a full admission block or a stable cross-restart identity (both rejected — see the panel synthesis doc): before dispatching a genuinely new `intentKey`, the gateway also checks whether the SAME tool (any arguments, any connection) has an unresolved (`dispatched`/`ambiguous`) intent belonging to a connection this gateway's own startup recovery flagged `pendingOperatorReview` — if so, the tool is quarantined (`-32082 GATEWAY_TOOL_QUARANTINED_PENDING_OPERATOR_REVIEW`) until an operator resolves that connection. Deliberately scoped to `pendingOperatorReview` connections only: normal concurrent use of the same tool across unrelated, healthy live connections is unaffected.

*Control:* `tests/gateway/proxy/run-tests.js`'s idempotency-key replay/no-key-supersede/mismatched-key and tool-quarantine cases (56/56 passing, along with the full existing `tests/gateway/*` and `tests/graphlint/gemini` suites, independently re-run against this exact change).

**Update (2026-09-12) — round-3 hardening from PR #33's re-review after E1/E2 landed.** All local implementation gaps in `recovery.js`/`gateway.js`/`proxy.js`'s own bookkeeping (none second-guessing the E1/E2 design itself): the `INITIALIZE`, `ANOMALY`, and `CALL_RESULT` WAL appends were unguarded (unlike the already-guarded `CALL_START`/`SESSION_START` appends) — a WAL failure on any of them could escape `handleMessage`'s own "never throws" contract; `INITIALIZE` and `SESSION_START` (`openConnection`) now persist their WAL event *before* committing the corresponding in-memory state, rolling back cleanly on failure instead of leaving a "ghost" session or an unrecoverable initialized flag, while `ANOMALY`/`CALL_RESULT` (recorded after the real outcome is already known, with no "don't dispatch" option left) are now best-effort: logged, never escaping. If E1's generation-supersede overwrites a `completed` intent and the new dispatch's own `CALL_START` WAL append then fails, the rollback now *restores* the exact pre-supersede record (full idempotency key/cached result/generation) instead of deleting it outright — a plain delete would have let a later request carrying the ORIGINAL idempotency key dispatch again instead of replaying it. The E2 tool-quarantine scan (`recovery.listAllIntents`) now fails closed (blocks via the existing `-32082` response) rather than letting an unrelated corrupt/unreadable intent file anywhere on disk reject the whole request with a generic `-32603`. An agent reusing an in-flight JSON-RPC id for a different operation is now rejected before a durable intent is ever created for it (previously: intent created, then `session.recordCallStart`'s own duplicate-id check threw uncaught, orphaning that intent). An intent an operator resolved `not-executed` (but whose owning crashed connection has not yet finished being cleaned up) now gets its own dedicated block code (`-32084 GATEWAY_OPERATOR_CONFIRMED_NOT_EXECUTED`) instead of silently falling through two wasted attempts into the generic `-32080 GATEWAY_AMBIGUOUS_RETRY`. `recovery-abandon`'s own `GATEWAY_BUNDLE_ID_COLLISION` handling now applies the same content-verification `recoverCrashedSessions` already does — it used to treat every collision as an expected repeated attempt and could silently discard a genuinely different session's only remaining record. `listActiveConnections` now returns a sorted (not raw `readdirSync`) order, since `recoverCrashedSessions` consumes it directly for chain-append sequencing. `gateway-recovery/`'s directories and files (WAL/intent records, holding raw goals/arguments/results) are now created `0700`/`0600` rather than the umask-dependent `0755`/`0644` default, so another local user on a multi-user host cannot read them. `doStop`'s shutdown loop now isolates a per-connection `closeConnection` failure (e.g. a corrupt intent file) so the writer-claim is still released and other sessions still close, instead of that one failure escaping shutdown entirely and leaking a stale claim. `buildHealthStatus`'s `recovery` field and the startup `RECOVERY_AMBIGUOUS_INTENT` log now both name the actual intent key(s) involved (a new `recovery.dispatched` list alongside the existing `in_flight` count; real keys in the log's `recovery-resolve` command instead of a literal `<key>` placeholder) rather than requiring an operator to hand-parse raw recovery files to find them.
